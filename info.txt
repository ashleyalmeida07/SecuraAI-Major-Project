1. Recon & Surface Mapping Flow
Input: a URL. Nodes: Crawler node (requests/Playwright, follows links, finds forms and API calls) → Endpoint Classifier node (LLM tags each URL as "auth page," "API," "static asset," etc.) → Surface Report node (writes structured JSON of the attack surface). This is the flow every other flow consumes as input, so build it first.

2. Security Header & Cookie Audit Flow
Input: the endpoint list from flow 1. Nodes: Header Fetcher node (hits each endpoint, grabs response headers) → Rule Checker node (compares against a checklist — CSP, HSTS, X-Frame-Options, cookie flags) → Severity Scorer node (LLM ranks findings). Simplest flow to build — mostly deterministic rule-checking with a thin LLM layer on top for prioritization.

3. Broken Access Control Flow
Input: endpoint list + any auth tokens you have. Nodes: Auth Stripper node (replays each request without credentials, or with a lower-privilege token) → Response Diff node (compares authenticated vs unauthenticated responses) → Access Violation Detector node (LLM flags cases where sensitive data leaked without proper auth). Needs a small test-account setup on your target app to be meaningful.

4. Injection Testing Flow (SQLi / XSS / command injection)
Input: endpoints with parameters or form fields. Nodes: Payload Generator node (LLM or static payload library generates test inputs per injection type) → Injector node (sends payloads, non-destructively) → Response Analyzer node (LLM checks for error leakage, reflected input, anomalous behavior indicating injection). This is the flow that benefits most from an LLM reasoning over raw responses instead of regex matching.

5. SSRF & Info Leakage Flow
Input: endpoints that accept URLs, file paths, or IDs as parameters. Nodes: Probe Generator node (crafts internal-IP/localhost/file:// style payloads) → Prober node (sends them) → Leakage Detector node (LLM checks if internal responses, stack traces, or file contents leaked back).

6. Static Code Analysis Flow
Input: a local repo path. Nodes: AST Parser node (Python ast or tree-sitter walks the codebase) → Pattern Matcher node (semgrep-style rules for known-bad patterns) → ChromaDB Retriever node (embeds each suspicious snippet, retrieves similar known-vulnerable examples from your seeded ChromaDB collection) → Confidence Scorer node (LLM decides real issue vs false positive using the retrieved context). This is the flow where ChromaDB actually earns its place.

7. Fix Generation Flow
Input: a confirmed finding from any flow above. Nodes: Context Retriever node (pulls matching secure-code examples from ChromaDB) → Diff Generator node (LLM writes a framework-specific patch) → Explainer node (LLM writes the "why this matters" text). Keep this as one shared flow all the other flows call into, rather than duplicating fix logic per category.

8. Orchestration Flow
Input: outputs from flows 1–7. Nodes: Merger node (dedupes overlapping findings) → Prioritizer node (sorts by severity) → Report Builder node (final JSON/PDF report). This is the top-level graph — in LangGraph terms, flows 2–6 can literally be subgraphs invoked as nodes inside this one.

Build order: 1 → 6 (since it's your ChromaDB showcase) → 2 → 3 → 4 → 5 → 7 → 8. Getting flows 1, 6, and 2 working end-to-end already gives you a demoable multi-flow system for your resume, even before the rest are done.

Recon & Surface Mapping (recon)

Purpose: Acts as the starting point. It crawls a target URL, extracts links and endpoints, and uses an LLM to classify them by type (e.g., API, Auth, Static).
Output: A structured attack-surface report.


Security Header & Cookie Audit (header_audit)

Purpose: Takes the endpoints discovered by the Recon flow, fetches their HTTP headers and cookies, and runs them against a Security Rules Engine (checking things like HSTS, CSP, X-Frame-Options).
Output: An LLM-scored severity rating and executive summary for any vulnerabilities found.


Static Analysis (static_analysis)

Purpose: Uses Semgrep for code pattern matching and integrates with our Upstash Vector Database (RAG). It matches code against known vulnerability patterns and uses an LLM to triage findings and generate fixes.
Output: Triaged security findings with suggested code fixes.
